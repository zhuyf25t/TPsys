# 2026-05-26 Battle API 类型安全与 APIMessage 结构问题

## 总结

当前 battle API 相比 sample 的主要问题不是功能不能运行，而是 API contract 的代数结构不清晰。

系统层已经提供了 `APIMessage[Response]`、`RegisteredAPIMessage`、`apiNameFromClassName` 等能力，但 battle 没有真正把每个 API 建模成 typed APIMessage。现在 battle API 仍然大量依赖 `String`、手写 JSON decode、手写错误 message 和 route 层调度，导致类型安全只停留在局部 domain object，到了 API 边界就被弱化。

## 1. APIMessage 放错层

当前 battle 的 APIMessage 文件位于：

- `services/battle/routes/BattleCommandAPIMessage.scala`
- `services/battle/routes/BattleQueueAPIMessage.scala`
- `services/battle/routes/BattleRoomAPIMessage.scala`
- `services/battle/routes/BattleStateAPIMessage.scala`
- `services/battle/routes/BattleResultAPIMessage.scala`

这不符合 sample 风格。

`APIMessage` 不是 route。它应该是 API contract + use case request message，应该放在：

- `services/battle/api`

`routes` 层应该只保留很薄的 HTTP adapter，例如把 `/api/{apiName}` 交给通用 `APIMessageRouter`。它不应该知道 battle command 如何 decode、queue 如何 join、service 返回哪些业务错误、错误如何映射成 battle error code。

## 2. apiTypes 没有复用 objects 的权威领域类型

`objects` 中已经定义了 battle 的领域对象和值对象，例如：

- `BattleId`
- `PlayerId`
- `TicketId`
- `RoomId`
- `BattleMode`
- `WeaponKind`
- `BattlePhase`

但 `apiTypes` 中又用 `String` 或 `Option[String]` 重新表达同一批业务概念。

典型问题：

```scala
final case class BattleCommandAPIRequest(
  battleId: String,
  playerId: String,
  ticketId: Option[String],
  ...
)
```

随后又在 `toCommand` 里手动转换：

```scala
BattleId.apply
PlayerId.apply
TicketId.apply
```

这说明 API 层没有真正使用 `objects` 作为单一事实来源，而是先构造了一个弱类型 DTO，再补救式转换成 domain object。

更合理的方向是 APIMessage 或 typed request 直接持有：

```scala
battleId: BattleId
playerId: PlayerId
ticketId: TicketId
```

JSON decoder 可以负责从 wire string decode 成这些 value object，但业务 API 类型本身不应该长期持有裸字符串。

## 3. ADT 和 enum 过早退化成 String

当前 API response 中大量字段使用 `String` 表达有限状态或业务类型，例如：

- `commandStatus: String`
- `commandReason: Option[String]`
- `status: String`
- `kind: String`
- `weaponKind: String`
- `phase: String`
- `message: String`

这些字段对应的业务概念本来已经有 enum / ADT，例如：

- `BattleCommandStatus`
- `BattleCommandReason`
- `SkillOutcomeStatus`
- `WeaponKind`
- `ProjectileKind`
- `BattlePhase`

正确边界应该是：

- Scala API contract 内部保留 enum / ADT。
- 只有 Circe `Encoder` / `Decoder` 在最终 JSON 边界调用 `wireValue` / `fromWire`。
- 不要在 API case class 字段里提前变成 `String`。

否则新增 enum case 时，编译器无法强制检查所有 response 映射是否更新。

## 4. 错误模型被 message: String 抹平

当前 `APIMessageError` 和 battle route support 使用：

```scala
BadRequest(message: String)
Forbidden(message: String)
NotFound(message: String)
```

battle route 中也大量出现：

```scala
badRequest("Invalid battle command request.")
notFound("battle_not_found")
forbidden("command_not_authorized")
```

这会把业务错误 ADT 抹平成字符串。

问题是：

- 错误原因没有稳定类型。
- 编译器无法检查错误分支是否穷尽。
- 前端 contract 只能依赖字符串约定。
- 错误 code、HTTP status、用户可读 message 混在一起。

更合理的方向是每个 API 有自己的 typed error ADT，例如 `BattleCommandAPIError`，最后由一个 encoder / presenter 统一映射到 HTTP status 和 JSON error response。

## 5. routes 层过厚

当前 battle route/APIMessage 文件承担了太多职责：

- JSON decode
- request validation
- service 调用
- domain error 到 API error 的映射
- API error 到字符串 message 的映射
- JSON response encode

这让 `routes` 变成了业务流程控制层，而不是 HTTP adapter。

sample 风格下，route 应该非常薄，只负责：

- 接收 HTTP request
- 交给 APIMessageRouter
- 返回 HTTP response

battle 的业务 API 行为应该集中在 `services/battle/api` 的 APIMessage 中。

## 6. apiTypes 当前不是合格的 APIMessage contract

现在的 `apiTypes` 更像 DTO + codec + projection helper 混合包，而不是 APIMessage contract。

它的问题是：

- request 和 response 没有围绕 APIMessage 聚合。
- error ADT、request DTO、response DTO、service command 转换分散。
- 同一个业务概念在 `objects`、`apiTypes`、`routes` 之间重复表达。
- `String` wire value 过早进入业务 API 类型。
- 不能充分利用 Scala 编译器检查 contract drift。

## 7. 正确方向

battle API 应逐步改成：

```scala
final case class BattleCommandAPIMessage(
  battleId: BattleId,
  playerId: PlayerId,
  ticketId: TicketId,
  ...
) extends APIMessage[BattleCommandAPIResponse]
```

其中：

- APIMessage 放在 `services/battle/api`。
- 字段优先使用 `objects` 中的 domain value object / enum / ADT。
- request decoder 负责从 JSON decode 成 typed APIMessage。
- response 保留 typed enum / ADT。
- error 使用 typed API error ADT。
- `wireValue` / `fromWire` 只出现在 Circe codec 边界。
- `routes` 只保留薄 HTTP adapter。

## 结论

当前 battle API 最大的问题是：domain objects 已经存在，但 API 层没有把它们作为单一事实来源，而是重新用 `String` 建了一套弱类型影子模型。

这导致：

- ADT 被字符串抹平。
- APIMessage 不是真正的 typed message。
- routes 层承担过多业务逻辑。
- apiTypes 不能作为稳定 contract。
- 前后端契约漂移无法在编译期充分暴露。

后续修复不应该先做大规模文件搬迁，而应该选一个 API，例如 `BattleCommandAPIMessage`，先完成一条 vertical slice：typed APIMessage、typed request fields、typed response fields、typed error ADT、Circe codec 边界、薄 route 注册。

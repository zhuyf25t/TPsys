# 第二章：掩盖延迟的“欺骗”

### 前言

在服务器权威的架构下，玩家按下一个键位，数据走到服务器，服务器算完会来，这段物理时间差（Ping 值）是不能消灭的。如果等待服务器会对游戏体验造成极大负面影响。

为了解决这种“界面卡顿”的问题，现代网络架构师发明了三大视觉“欺骗”魔法。这是我们理解和指导 claude 构建项目的核心逻辑。

---

### 本地移动预测 Client-side Prediction

当我们按下一个键位，等 50ms 后服务器批准了我们才真正显示出来移动，这种“黏手感”是 MOBA 玩家绝对不能忍受的。

我们采用 **“先斩后奏”** 的办法**欺骗**玩家，客户端立刻在本地运行一遍物理计算（判断有没有撞墙、速度是多少），直接将玩家画面往前推，**而不等服务器回话**。同时将按键操作发给服务器。

首先，这要求**客户端**和**服务器**的**物理引擎**的基本逻辑是一致的。然后，如果这样的体验仍然不佳，我们需要用到第二个手段。

---

### 服务器对帐与重演 Server Reconciliation

既然客户端“先斩后奏”，如果客户端算出的坐标，和服务器算出来的坐标不一样（比如服务器算出来玩家被小兵卡了一下），如何处理？

首先听谁的？显然**听服务器的**。但是客户端的画面应该如何纠正？

一种粗糙的纠正方式：**Lerp (Linear interpolation)** ：一个用于实现数值之间平滑过渡的对象，在指定时间内将一个数值平滑过渡到另一个数值（简单来说就是**一次函数**）。当误差过大时，可以“硬跳”（直接把玩家瞬移过去）；当误差较小时，按一定比例的速度悄悄把玩家拉过去（例如固定的 24\%/帧）。

上述纠正方式的问题在于，首先我们在**对抗玩家的手感**，然后这是 **“收敛但永不抵达”** 的数学模型，我们会有**阈值断层**的现象，Lerp 在图形学中应用更常见。一种显而易见的优化方式是，通过**平滑的调整速度矢量**去从当前位置靠近实际位置。我们会在下面介绍。

**历史重演：**

1. 客户端把**自己的**每一次按键和时间戳（Tick 序号）存进一个本地列表（**我们不能对“别人”进行历史重演**，因为我们根本不知道别人按了什么键，别人发来的只有客观的位置快照）。
2. 当服务器说“玩家 A 第 100 帧位置是 X”时，客户端立刻将玩家的真实坐标设为 X。
3. 此时客户端可能已经跑到了第 105 帧。客户端需要在一瞬间，把 101 到 105 帧之间的按键，基于服务器给的正确坐标，**重新快速**计算一遍。
4. 在理想情况下，瞬间重新算出来的坐标，会和屏幕上的预测坐标完美重合。

然而事实并不总是理想情况。例如第 102 帧在玩家的屏幕上没有小兵但到实际的第 102 帧时有个小兵被推了过来挡住了路，接下来**两者就会产生巨大的鸿沟**。

**也即，重演不能“消灭”误差，只能“最小化”误差。** 因为服务器发的始终是过去的数据，没有重演时，我们会在屏幕中一直闪现。

---

### 实体插值 Entity Interpolation

**重演之后的两种“平滑追赶”的处理方案：**

1. **动态 Lerp 消减**：根据距离动态计算 Lerp 的权重。距离越远，抽取的百分比越高，让它快点归位。距离越近，百分比减小，让它慢慢融合。
2. **误差偏移量 Error Offset 衰减（主流方案）** ：

   > 《守望先锋》等 3A 大作常用的技术。
   >

   **记录误差**（收到服务器并重演的一瞬间，算出误差向量 $E = 预测位置 - 重演位置$）；**视觉欺骗**（让渲染位置始终等于原本位置 $+E$，此时玩家看到的位置还是原来的位置，尽管逻辑上已经跳走了）；**慢慢消除误差**（接下来的几帧里，不断让 $E$ 乘以一个衰减系数，例如 $0.9$）；**视觉效果**（玩家会看到小人非常自然地在移动中“微微平移”了一下，纠正了航向且没有闪烁感）。

   **帧率无关的指数衰减（工业界的神！）** ：利用自然常数 $e$ 和两帧之间的时间差 $\Delta t$，实现了一个**完美与帧率脱钩的动态衰减**。在数学上保证无论是 30 帧还是 240 帧运行游戏，1 秒后摄像机追赶的距离绝对相等。

**插值缓冲区 Interpolation Buffer**：针对网络抖动 Jitter 极度严重的情况，让客户端永远只看**过去**，例如收到服务器 100 帧的消息，客户端渲染的是第 90 帧。这会增加 10 帧的基础延迟，但能给“重演”留出极大的缓冲空间，可以用极其优雅的曲线平滑所有跳变。*这也是为什么视频直播会比现场慢个三秒钟，因为如果网络突然卡顿了，直播里会还有缓冲可以播，而如果真的完全实时直播的话，如果网络不稳定会导致传包的时候显示的屏幕也随着传包频率而走走停停。*

**注意**，插值缓冲区**不是**重演之后的一种处理方案，**插值缓冲区是专门留给别人的时光机。**

需要“彻底放弃”平滑的场景：**传送门**、**死亡复活**。这被称作“死亡绕过 Death Bypass”或“硬跳”，当玩家死亡、复活、石化时，必须立刻中断所有的 Lerp 和缓冲，瞬间应用最新状态（否则会出现幽灵死后往前飘了 100ms 的诡异画面）。

---

### 划清“我”与“世界”的界限

注意！下面的**本地玩家**和**非本地玩家**是指，**自己电脑屏幕中（前提）** 的**玩家自己**和**其他玩家**。

我们的系统架构中，必须明确区分两个完全不同的数据流管道：

1. **处理“本地玩家” The Local Player**

核心目标：极致的响应速度（0 延迟感知）。核心工作流：本地预测 $\to$ 收到回包 $\to$ 历史重演 $\to$ **误差偏移量衰减 Error Offset**。

在本地玩家的处理方案中，**绝对不要使用“插值缓冲区 Interpolation Buffer”** ，如果加上缓冲相当于我们的操作会失去所有动作敏捷性。

2. **处理“远程实体” Remote Entities - 敌人、队友、投射物**

核心目标：绝对的视觉平滑，掩盖网络抖动。核心工作流：收到服务器状态 $\to$ **存入插值缓冲区 Interpolation Buffer** **$\to$** 强制延迟 100ms 渲染 $\to$ 使用 **Lerp** 连线。

**插值缓冲区是专门留给别人的时光机。** 对于远程实体，我们只看过去，在两个历史快照之间用纯粹的数学 Lerp 平滑过去，不涉及任何物理碰撞检测和状态推演。

简单总结一下就是：

1. **骗过自己的手：本地预测 + 重演 + Error Offset。**
2. **骗过自己的眼：插值缓冲区 + Lerp。**

---

### 总结

主线：确定服务器全文 $\to$ 必然带来延迟 $\to$ 需要使用三类手段掩盖延迟。

**最重要的事情**：我们必须保证我们的前端 TypeScript 和后端 Scala 有一套一模一样的移动和碰撞计算函数。

在帧同步 Lockstep 中任何浮点误差都会导致“蝴蝶效应”因此绝对需要避开浮点数。但在状态同步 State Sync 构架下，服务器会高频发绝对位置作为做高裁决，浮点数的误差会被 Error Offset 瞬间平滑掉。虽然统一双端逻辑仍然重要，但在状态同步中，不需要对浮点数有过度避让。

简单来说，这是一种 **“收束世界线”** 的哲学，我们需要研究如何将多个平行宇宙一样的世界，融合到主线中。

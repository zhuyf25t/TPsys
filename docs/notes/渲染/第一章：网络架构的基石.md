# 第一章：网络架构的基石

### 前言

在构建任何多人游戏之前，架构师必须面对的三个核心的物理与逻辑课题：

1. **连接方式 Topology**：玩家的设备如何相互交换数据？
2. **信任机制 Authority**：当数据发生冲突时，系统听谁的？
3. **同步机制 Synchronization**：我们要在网络中传输“动作”，还是传输“结果”？

---

### 网络拓扑：设备如何对话

**网络拓扑 Network Topology**：网络中各个设备（计算机、路由器、交换机等）的**物理布局（物理拓扑：线缆、设备的实际摆放方式）** 或**逻辑连接（逻辑拓扑：数据包在网络中穿梭的路径和规则）** 的“地图”。

- **点对点架构 Peer-to-Peer / P2P**

在 P2P 架构中，玩家的电脑直接相互连接，形成一个完全图，这在网络架构中也被称作**全网状架构**。也就是说，如果房间里有 $n$ 个玩家，在逻辑拓扑中的连接的边数是 $n \cdot (n-1)/2$。

>  **《帝国时代》初代 (Age of Empires, 1997)**  是一款经典的**即时战略（RTS, Real-Time Strategy Game）游戏**：一种非回合制的策略游戏，玩家需要在实时环境中进行决策和指挥，以达到游戏目标。
>
> 同步机制：使用**确定性锁步同步 Lockstep** 技术，核心思想是所有客户端**在相同的初始条件和输入**下，确保每个游戏状态的计算结果完全一致，因此只发送控制输入而非整个状态，显著减少网络宽带的需求。*传输位移，根据位移和起点得到终点。*

**优势**是极低的理论延迟和不需要中心化服务器；**劣势**是难以扩展、存在主机优势、房主掉线后需要暂停和进行复杂的主机迁移、极易作弊。

在 P2P 中，玩家 A 向玩家 B 发起了交互，信息包会由玩家 A 发出给其他全体玩家，玩家 C 和玩家 D 都会得知“玩家 A 向玩家 B 发起了交互”这一事实。*这也导致防作弊变得困难，因为一个玩家想要作弊只需要通知其他全体玩家一条虚假信息就行。*

P2P 遇到**数据冲突**的处理方式：

1. **锁步同步 Lockstep**： **“少数服从多数”** 或 **“绝对一致”** ，每一帧所有人的指令必须全部到齐后才能同步运行下一步。
2. **状态竞争 State Contention**： **“房主优先”** ，为什么 P2P 中会出现房主？这并不是中心化，房主的作用是仲裁者，当遇到数据冲突时，由房主来裁定最终结果。
3. **最终一致性 CRDTs** (conflict-free replicated data type 无冲突复制数据类型)  **/ 区块链逻辑**： **“算法决定”** ，给每个动作打上精确到微秒的时间戳，当指令冲突时，根据预设的规则决定（例如时间戳早的胜出），对于算错了的部分，系统会强行**回滚 rollback** 到正确的状态。

- **客户端-服务器架构 Client-Server, C/S**

现代游戏的绝对的主流。机制是所有玩家 Client 互不通信，只与一个位于中心节点的服务端 Server 建立单一连接。也即 $n$ 个玩家有 $n$ 条连接。

**优势**是拓扑结构简单、服务器有全局视角易于管理和仲裁；**劣势**是所有数据必须经过服务器中转、物理距离会导致基础延迟（Ping 值）、服务器有算力成本。

### 权威模型：谁掌握了“真理”？

如果将游戏比作一场比赛，权威模型决定的是 **“谁是裁判”** 。在 C/S 架构下，**逻辑计算的权力**是可以分配的，我们需要决定如何分配，也即 **“权威 Authority”** 的归属。

- **客户端权威 Client Authoritative**

这种模式下，服务器放弃“思考”和“验证”，**只是担任一个“复读机”** ，把所有逻辑计算交给玩家的电脑。当玩家 A 的电脑运行代码时发现玩家 A 的子弹和玩家 B 产生了碰撞，玩家 A 的电脑会直接告诉服务器：“A 打中了 B，你广播一下”，于是服务器不加思考的对所有人喊“A 说打中了 B，B 扣血”。

>  **《元气骑士》** 的局域网联机、 **《饥荒》** 等以 **PVE（玩家对战环境）** 为主的游戏。
>
> 即使有玩家作弊，也只是破坏了自己的体验，不会严重伤害其他人的利益。

**优势**是极致的响应速度；**缺陷**是零反作弊能力，这是致命缺陷，绝对不能用于严肃的 **PVP（玩家对战）** 竞技游戏。

- **服务器权威 Server Authoritative**​**$\iff$**​**纯粹的 C/S**

服务器是唯一的真理源头（唯一的**大脑**），客户端被降级成一个“输入收集器”和“画面渲染器”（没有灵魂的**投影仪**）。客户端只能发送盲目的输入输出（如按下的按键、鼠标的角度），服务器在自己的内存中运行一套完整的物理引擎，最后将结果告知客户端。

>  **《战地》、《反恐精英 CS》**

**优势**是杜绝了大多数恶意的逻辑作弊；**挑战**是引入了不可忽视的输入延迟，每走一步都要等待一个**往返时间 RTT**，需要特殊处理让游戏变得可玩。

- **折中方案：客户端预测与回滚 Client-side Prediction & Rollback**

主要是解决服务器权威的卡顿。当玩家按下某个键位时，客户端首先**盲目乐观**的认为服务器一定会允许移动，在本地先把画面刷新了（**客户端预测 Prediction**），而不再等待服务器回包；服务器收到客户端的指令后在后台算出正确信息，发包给客户端（**服务器校验 Validation**）；如果对上了岁月静好，如果对不上，客户端必须无条件听从服务器，**强行把玩家拉到服务器指定的数据上**（**回滚与修正 Rollback / Reconciliation**）。

这也是为什么在玩网游网速不好的时候，会遇到 **“瞬移 / 拉回”** 现象，那是因为客户端的预测和服务器的真理发生了冲突，真理强行修正了预测。

服务器在其中起到了**验证**和**纠偏**的作用，带来的两个有趣现象： **“橡皮筋”效应 Rubber Banding**，往前跑三步就会被拽回原点一步； **“延迟击中” Favor the Shooter**，有时在服务器端做验证时可以宽容一点，比如服务器判定未击中，但是客户端发来的时间戳显示在本地确实是瞄准的，服务器出于照顾客户端体验的目的，会判定击中，这是一种**延迟补偿 Lag Compensation**。

> 只要是涉及 **“多人、竞技、高频率操作”** 的游戏，基本都属于这一范畴。
>
> **FPS（第一人称射击）：《反恐精英 CS2》、《守望先锋》、《Valorant》、《战地》。** 在这类游戏中，网速慢会导致例如开门时“开门又关门”或者走两步退一步，这是服务器在**纠偏**。
>
> **MOBA（多人在线竞技）：《英雄联盟 LoL》、《Dota 2》。** 这类游戏通常采用更严格的校验，英雄移动非常准，但如果延迟高，英雄会需要过很久才会移动（因为它们有时会减少预测，以保证操作的绝对精准）。
>
> **大逃杀：《绝地求生 PUBG》、《Apex 英雄》。** 百人同场竞技，服务器压力巨大，验证和纠偏频率会动态调整。
>
> 以及 **slay.one**。

### 核心同步流派：动作 vs 状态

多人游戏架构中最深奥也最决定底层代码结构的抉择。同样是服务端权威，我们如何在网络中**传输数据**？

- **帧同步 Deterministic Lockstep**

帧同步的哲学是，**给定相同的初始状态和相同的输入，两台计算机必然得到完全相同的结果。** 服务器在整个游戏过程中**只负责转发玩家的操作指令**，所有客户端收到指令后各自在本地的 CPU 里模拟出完全一致的战斗画面。

>  **《魔兽争霸 3》、《星际争霸》、《王者荣耀》** 等**大多数 RTS 和部分 MOBA 游戏**。

**优势**是宽带消耗极低（只需传输键盘按键）；天然支持完美的录像回放（只需保存一局游戏所有的按键记录，重新播放即可）。**严苛的要求**是必须保证“严格的确定性”，这意味着不能使用标准的浮点数，不能使用普通的随机数，此外**断线重连**非常痛苦（玩家掉线后必须从头开始快进接收确实的所有操作指令，也称 **“追帧”** ）。

- **状态同步 State Synchronization**

状态同步的哲学是，**客户端不需要懂规则，只要把服务器发来的“照片”连起来播放就行。** 服务器独立运行所有复杂的计算，然后以极高的频率（例如 60Hz，即每 16 毫秒）对整张世界拍一张包含所有人坐标、血量的“快照（Snapshot）”，并将其群发给所有客户端。

>  **《守望先锋》、《绝地求生》、大型 MMORPG（如《魔兽世界》）。**

**优势**是开发简单（无需“确定性物理引擎”），断线重连极快（玩家只需要最新的一张“世界快照”）；**劣势**是极高的带宽压力，每次广播的快照会变得非常大，对服务器性能有极大考验。

### 架构师的十字路口——业界大厂的抉择与 Web 端的困境

经典游戏构架大起底。

- **帧同步 Deterministic Lockstep：“确定性的暴君”
  代表作：《王者荣耀》、《皇室战争》。**

服务器绝不计算物理和伤害，只负责把按键广播给所有人，所有人手机拿到按键后自己在本地算结果。帧同步的致命弱点是不能丢包、不能停顿。如果玩家断线 1 分钟，重连时必须把这一分钟内所有的按键全接受一遍，然后在本地“快进”播放（追帧）。

如果在网页中做帧同步，玩家把浏览器切到后台，浏览器会强行暂停渲染，切回来时需要瞬间补算物理碰撞而崩溃。

- **纯服务端权威 + 状态同步：“富有的独裁者”**   
  **代表作：英雄联盟（PC 端）、slay.one 知名网页射击游戏。**

服务器掌控一切，每秒向客户端发送世界状态快照。

英雄联盟的英雄会“楞”个几十毫秒才走，LOL 相当克制，因为 MOBA 游戏中有极其复杂的动态碰撞，宁可有一点点固定的输入延迟，也绝对不能接收画面的位置是假的，或者发生瞬移回拉。这也就意味着，玩家感受到的延迟，等于真实的物理延迟（Ping 值），因此重度依赖极好的网络基建（拳头公司搭建了著名的 Riot Direct 网络）。

Slay.one 通过 WebSocket 传输状态，但也面临且后台的问题。

- **客户端权威 / 弱验证：“基于信任的狂欢”**   
  **代表作：《元气骑士》（早期局域网）。**

谁是主机谁说了算，打中没打中全凭客户端自觉上报，开发极其简单，手感极其完美（根本没有服务器延迟这件事情），但拿到公网上，将充斥着各种外挂。

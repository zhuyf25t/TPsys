# 第四章：延迟补偿与命中判定

### 前言

在前三章中，我们的游戏有了坚实的骨架：本地玩家的移动**敏捷**（预测与重演），其他玩家的移动**丝滑**（100ms 的插值缓冲），枪口的火花与屏幕的震动能**瞬间**点燃玩家的肾上腺素（表现与状态分离）。

然而在这完美的幻象下，隐藏着网络射击游戏中最古老、也最致命的逻辑撕裂，由于“表面”和“真理”权衡下存在的时差，我们需要面对，**穿越时空的审判**。

---

### 悖论：幽灵与肉身

我们为了保证其他玩家的丝滑移动，客户端在渲染时，永远是读取他们 100ms 之前的**历史快照**。这意味着一个极其反直觉的物理事实：**你在屏幕上看到的敌人，并不在那个位置。**

- **渲染层（幽灵）** ：你的屏幕上画出的敌人模型，滞后了 100ms。
- **逻辑层（肉身）** ：服务器内存中记录的、此时此刻敌人真实的**物理碰撞盒 Hitbox**。

作为人类玩家，我们的眼睛看到的只有“幽灵”（所以我们的准星也自然只会对准“幽灵”）。如果服务器很呆，在收到我们的开枪指令后，用此时此刻的“肉身”位置去做碰撞检测，结果就是，**我们绝对打不中一个正在移动的敌人**。因为 100ms 的延迟里，加上我们自身网络 ping 传输消耗的时间，敌人的“肉身”早已跑到几个身位之外。

为了解决这一巨大的不公平，工业界诞生了一项堪称神迹的技术。

---

### **时光倒流 Lag Compensation**

大厂的架构师想出了一个极其霸道但相当优雅的解法：**既然玩家只能瞄准过去，那服务器就陪着玩家回到过去。**

这项技术被称作**延迟补偿 Lag Compensation**，最早由 Valve (V社) 开发《半条命》和 Source 引擎时发扬光大。

**算法工作流：**

1. **建立历史档案馆**：在后端，我们需要建立一个极其高校的**环形数据结构 Circular Buffer**，保存过去 1 秒内（大约 60 帧）每一次 Tick 时所有玩家的精确物理碰撞盒。
2. **时间戳截获**：本地玩家开枪，客户端的指令不仅包含射击的指令，还隐式或显式地附带了玩家当前得网络延迟 ping 和系统的插值延迟 Interpolation Delay。
3. **时空回溯**：服务器收到开枪指令，做了一个疯狂的决定，**暂停当前的世界**。它根据玩家的延迟计算出，“当这个玩家开枪的那一瞬间，他的眼睛看到的是多少毫秒前的世界”（假设是 150ms）。
4. **历史审判**：服务器把被击中者的物理碰撞盒，瞬间从当前位置，拉到 150ms 之前的那个历史档案的位置。在这个历史时空中，服务器沿着玩家开枪的角度发射一条射线，如果射线穿过了那个被拉回来的碰撞盒，判定击中。
5. **拨乱反正**：判定结束后，碰撞和瞬间归位到当前时间，游戏继续，被击中者扣血。

> **《CS:GO / CS2》的红蓝方块**
>
> 如果玩家开启过一些控制台指令，就会在开枪时，看到屏幕上出现的两种颜色的方块。
>
> - 红方块（客户端计算）：本地电脑认为你打中的位置；
> - 蓝方块（服务端计算）：这是服务器经过时光倒流后，确认你打中的位置。
>
> 只有蓝方块判定击中才会真正扣血。这也是为什么玩家看到飙血了但对方没扣血，在服务器极度严苛的时空回溯中，判定出现了微小的误差。

### 架构哲学碰撞：射手优势 VS 绝对公平

引入延迟补偿意味着，带来了一个无法回避的副作用： **“隔山打牛”（有掩体击杀）** 。

你在被一个高延迟（Ping 150ms）的狙击手追杀，一个滑步躲到了墙壁后面，松了一口气，但在那个高延迟狙击手的屏幕上你还没有进墙壁，于是他开枪了。服务器回溯时间，发现在他开枪的一瞬间你确实还没进墙壁。于是**你明明躲到了墙壁后面，却被击中**。

在这一问题中，工业界分裂成了两大阵营。

- **Favor the shooter 射手优势**

>  **《守望先锋》Overwatch**

暴雪的工程师明确提出这一概念，基本哲学是，**开枪者的体验是第一位的。**

如果不做延迟补偿，开枪的人会觉得自己明明瞄准了却打不中，这种挫败感是毁灭性的，虽然被打的人躲在墙后被击中会觉得委屈，但这是为了游戏整体的爽快感必须付出的代价。

$\todo{如果我们希望普通玩家（哪怕网络有波动）也能感受到枪枪到肉的爽快感，应当拥抱射手优势}$  

**一些射击的技术：**

1. **带阈值的时光倒流 Bounded Rollback**：如果未来加入了即时命中 Hitscan 的武器（比如狙击枪、激光），在后端做历史回溯，设定一个 MAX\_REWIND\_TIME = 200ms。

   如果开枪者延迟超过 200ms，服务器最多只能倒带 200ms，超过这个极限的延迟，就需要他自己承担打不中的后果。我们要保护普通玩家，而不纵容“火星网络”（对实时消息闭塞或知晓滞后的人群）。

   > 《战地》大战场游戏，照顾全球各地的玩家，有时会把补偿上限开到 200ms 甚至 250ms。
   >
   > 《CS:GO》或《Valorant》这类极其强调电竞公平的游戏，会将最大补偿上线卡得很紧（通常 100ms - 150ms 之间）。如果 ping 超过了这个值，相当于系统认为你的网络需要为你的射击状况负责。
   >
2. **针对子弹和近战的优化**：**相当重要！！！** 对于有带速度向量的飞行子弹 Projectiles 和近战挥砍 Slashes，对于这类武器，业界有一种更廉价的“射手优势”的实现方式，**体积补偿 Hitbox Expansion**，后端计算碰撞时，当一发子弹靠近敌人时，稍微把敌人的服务端碰撞体积 Hitbox 向**敌人过去 100ms 所在的位置**拉长一点，形成一个“胶囊体”。这样既不需要复杂的时光倒流，又能极大程度的让开火者觉得“打中擦边球”，用极其低廉的 CPU 算力完美实现了射手优势。

简而言之，让开火的人爽，是游戏的最高优先。

- **克制的补偿与基建碾压**

>  **《Valorant》无畏契约**

拳头公司 Riot Games 为了追求极致的硬核电竞公平，对“射手优势”进行了极度严格的限制。如果服务器回溯时间时，发现受击者**在逻辑上**已经进入了掩体，《Valorant》的服务器有时会无情的拒绝这次击中判定。

为什么回溯了时间还会有**逻辑上的不同**？倘若一个延迟 150ms 的玩家击中了另一个延迟 100ms 的玩家，在时空回溯时服务器发现前一个玩家击中了后一个玩家，但后一个玩家已经躲进了掩体：“虽然回溯显示你打中了，但因为你的延迟太高，这次命中对那个已经躲好的玩家不公平，所以我拒绝这次伤害”。

为了留住游戏客户，拳头游戏公司**砸钱搞基建**，铺设了全球性的 Riot Direct 专用网络，强制把所有人的 Ping 压在 30ms 内。

### 区分武器类型 Hitscan vs Projectile

在实现延迟补偿之前，作为架构师，我们必须区分我们游戏中的武器类型，因为它们对服务器算力的要求截然不同：

1. **即时命中 Hitscan**：比如激光枪、狙击步枪。子弹没有飞行时间，开枪瞬间到达目标。**这类武器必须使用延迟补偿，而且需要极其严密的历史碰撞盒回溯算法。** 如果游戏中有这类武器，我们必须在后端用高效的数据结构维护这段历史轨迹。
2. **飞行道具 Projectile**：比如火箭筒、缓慢飞行的能量球。

   当子弹是在空中飞行时，对于这类有飞行轨迹的武器，业界通常**不做、或只做极其轻量的延迟补偿。**

   **原因**是，玩家在发射火箭筒时，本来就需要“预判”敌人未来的走位。既然大脑已经进入了这种“预判模式”，那么那 100ms 的网络延迟，完全可以被玩家的大脑计算的“预判提前量”给悄悄吸收掉，这能给后端节省海量的 CPU 算力。
